## 1. Удаление папки оставляет её изображения в поиске

- [x] Исправлено и проверено.

Проверка: Android-тесты удаляют папку и проверяют галерею, поиск, счётчик, OCR и FTS; проверены повторное добавление, пересекающиеся деревья и удаление во время сканирования/OCR. Связи `folder_images` сохраняют доступ через оставшуюся папку; исходные файлы не удаляются.

**Место:** `app/src/main/java/com/darkesttrololo/memeizer/data/folder/FolderRepository.kt:23`, связанные DAO и сущности в `data/db/`.

Удаляется только запись `indexed_folders`. Каскадных связей нет, а запросы галереи и поиска не проверяют принадлежность к выбранным папкам. Изображения и распознанный текст остаются доступны после удаления папки из настроек.

**Сценарий:** добавить папку, проиндексировать изображение с известным текстом, нажать `Remove`. Проверить галерею, поиск по этому тексту и счётчик изображений.

**Ожидаемое исправление:** согласованно очищать связанные изображения, OCR и FTS-записи. Учитывать активную индексацию: задача, ранее прочитавшая список папок, не должна заново добавить данные удалённой папки. Проверить поведение при повторном добавлении папки и пересекающихся выбранных папках.

## 2. Переиндексация не удаляет записи исчезнувших файлов

- [x] Исправлено и проверено.

Проверка: Android-тесты заменяют полный снимок папки после перемещения/удаления и проверяют очистку всех таблиц. Пустая папка очищается; исключение и отмена сохраняют индекс. Реальный `FolderScanner` отдельно проверен на вложенных каталогах, null-курсоре, loading/error и ошибке частичного обхода.

**Место:** `app/src/main/java/com/darkesttrololo/memeizer/data/indexing/IndexRepository.kt:28`, `data/folder/FolderScanner.kt`.

Обход только добавляет и обновляет найденные изображения. Удалённый или перемещённый файл остаётся в базе и результатах даже после `Reindex now`, хотя его URI больше не работает.

**Сценарий:** проиндексировать папку, удалить одно изображение вне приложения, запустить переиндексацию. Повторить с перемещением изображения.

**Ожидаемое исправление:** после успешного полного сканирования папки удалять отсутствующие изображения и связанные OCR/FTS-записи. Отличать успешно прочитанную пустую папку от ошибки доступа, частичного обхода и отмены задачи: не очищать индекс на основании неуспешного сканирования.

## 3. Параллельные запуски индексации конфликтуют при записи

- [x] Исправлено и проверено.

Проверка: два экземпляра репозитория с общей базой запускаются одновременно с управляемой приостановкой OCR; проверены первая индексация, принудительная повторная, отмена и следующий запуск. В базе одна запись изображения/OCR/FTS. SQLite-триггер искусственно прерывает сохранение статуса и подтверждает откат всей транзакции.

**Место:** `app/src/main/java/com/darkesttrololo/memeizer/data/indexing/IndexRepository.kt:72`, `IndexScheduler.kt`, `IndexWorker.kt`.

Ручная и периодическая задачи имеют разные unique work names и могут пересекаться. Общей блокировки репозитория нет; mutex в `NcnnPaddleOcrEngine` защищает только PaddleOCR. Сохранение OCR, FTS и статуса выполняется отдельными операциями.

При чередовании `delete(A) → delete(B) → insert(A) → insert(B)` для одного изображения вторая вставка нарушает уникальность `ocr_results.image_id`. Исключение из блока `onSuccess` не обрабатывается последующим `onFailure` этого же `Result`, и задача завершается ошибкой. Аналогично нужно учитывать гонку между поиском существующего изображения и вставкой по уникальному URI.

**Сценарий:** два одновременных вызова индексации одной папки, включая принудительную переиндексацию уже известного изображения. В тесте желательно управлять чередованием операций, а не полагаться на случайный тайминг.

**Ожидаемое исправление:** сериализовать работу с общим индексом и атомарно сохранять OCR, FTS и статус. Не держать транзакцию базы на протяжении длительного OCR. Проверить отсутствие конфликтов уникальности, дублей FTS и несогласованных состояний, включая отмену и замену ручной задачи. Согласовать решение с удалением папок из пункта 1.

## 4. Компаратор OCR-строк нарушает транзитивность

- [x] Исправлено и проверено.

Проверка: тестируется непосредственно функция сортировки приложения на Android: пример A/B/C, строки и колонки, пустой и одиночный списки, 100 наборов по 100 элементов с Random(0). Исключений нет, элементы сохраняются, повторная сортировка не меняет результат.

**Место:** `app/src/main/java/com/darkesttrololo/memeizer/data/ocr/NcnnPaddleOcrEngine.kt:80`, функция `sortTextLines`.

Для близких значений Y компаратор сравнивает X, а для остальных — Y. Это допускает циклический порядок и исключение `Comparison method violates its general contract!`. Ошибка сортировки приводит к неуспешному OCR изображения.

**Минимальный пример:** при высоте всех рамок 24 вычисляется `rowTolerance = 18`. Пусть пары `(минимальный X, центральный Y)` равны `A=(30,20)`, `B=(20,35)`, `C=(10,50)`. Текущий компаратор возвращает `A > B`, `B > C`, `C > A`.

**Ожидаемое исправление:** использовать устойчивый порядок, например сначала распределять строки по группам, затем сортировать группы по Y, а элементы внутри группы по X. Проверить расположение текста в несколько строк и колонок, пустой список и одиночную строку.

**Проверка ревью:** отдельное JVM-воспроизведение того же компаратора на 100 элементах с одинаковой высотой рамки 24 вызвало указанное исключение. Генератор `java.util.Random(0)`, для каждого элемента `x = nextInt(300)`, `y = 20 + nextInt(150)`; ошибка возникла на наборе с индексом 8 при последовательной генерации наборов, начиная с 0. Это эксперимент с компаратором, а не запуск Android-кода.

## 5. Числовой поиск совпадает с внутренними ID изображений

- [x] Исправлено и проверено.

Проверка: на Room/SQLite изображение с ID 1 и текстом cat не находится по `1*`; после OCR текста number 1 находится. MATCH ограничен колонкой text, дополнительно учитывается статус INDEXED.

**Место:** `app/src/main/java/com/darkesttrololo/memeizer/data/db/Entities.kt:53`, поисковый запрос в `Daos.kt`.

FTS индексирует обе колонки: `text` и `image_id`. Выражение `meme_search_fts MATCH :query` ищет по всей таблице. Поэтому запрос `1` находит изображение с ID 1, даже если OCR содержит только `cat`.

**Сценарий:** создать запись с `image_id = 1` и текстом `cat`, выполнить запрос `1*`. Он не должен возвращать эту запись. При этом изображение, в тексте которого действительно есть число 1, должно находиться.

**Ожидаемое исправление:** исключить `image_id` из индексируемых колонок либо ограничить поиск колонкой текста. Если меняется схема базы, обеспечить обновление существующей базы без необоснованного удаления пользовательских данных.

## 6. Служебные названия OCR-движков загрязняют поиск

- [x] Исправлено и проверено.

Проверка: пустой результат OCR не находится по названиям движков/языков, реальное latin находится. Миграция 1→2 проверена открытием базы через Room с валидацией схемы: FTS перестраивается из OCR без старых заголовков; выбранная папка, изображения, реальные латинские/кириллические слова и числа сохраняются.

**Место:** `app/src/main/java/com/darkesttrololo/memeizer/data/indexing/IndexRepository.kt:127`, формирование `combinedText` и запись в FTS.

Заголовки `[paddleocr-ncnn:cyrillic]` и `[mlkit:latin]` сохраняются вместе с распознанным текстом в FTS. Запросы `latin`, `mlkit`, `cyrillic` и их префиксы находят изображения независимо от реального содержимого, даже если оба движка вернули пустой текст.

**Сценарий:** проиндексировать изображение без распознанного текста; поиск по названиям движков и языков не должен его находить. Если слово `latin` действительно присутствует на изображении, поиск должен работать.

**Ожидаемое исправление:** отделить метаданные движков от текста для поиска. Учесть уже сохранённые FTS-записи: обычная индексация пропускает неизменённые изображения со статусом `INDEXED`, поэтому исправление только новых записей оставит старую проблему. Выбрать и проверить способ обновления существующего индекса.

## 7. Ошибка повторного OCR оставляет прежний текст в поиске

- [x] Исправлено и проверено.

Проверка: после изменения contentKey и ошибки OCR старый текст исчезает; успешный повторный OCR возвращает поиск по новому тексту. Проверены отсутствие старой FTS-записи после отмены и атомарность записи при ошибке базы.

**Место:** `app/src/main/java/com/darkesttrololo/memeizer/data/indexing/IndexRepository.kt:89`, обработка ошибки в `runOcr`.

При ошибке обновляются OCR-запись и статус изображения, но старая FTS-запись остаётся. Поисковый запрос не фильтрует статус. Если содержимое изображения изменилось, а новое распознавание не удалось, оно продолжает находиться по прежнему тексту.

**Сценарий:** успешно проиндексировать изображение с текстом A, изменить его содержимое и смоделировать ошибку нового OCR. Поиск A не должен возвращать устаревший результат. После успешного повторного OCR поиск по новому тексту должен восстановиться.

**Ожидаемое исправление:** инвалидировать устаревшую FTS-запись либо явно учитывать актуальность результата при поиске. Изменение состояния должно быть согласованным с транзакционным сохранением из пункта 3.
